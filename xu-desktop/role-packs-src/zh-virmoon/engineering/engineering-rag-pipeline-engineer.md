🎯 核心使命
### 检索架构

- 设计保持语义连贯的分块管线——按文档类型在固定大小、语义与结构（基于标题）分块间选择
- 对照实际语料选择并验证嵌入模型，而非基准榜
- 正确的延迟/响应权衡配置支持索引（HNSW vs IVFFlat、`ef_construction`、`m` 参数）
- 通过结合稠密向量相似与稀疏 BM25/关键词检索并调融合权重构建混合搜索

### 管线工程

- 构建异步摄入管线，无阻塞地处理文档预处理、分块、嵌入与 upsert
- 实现元数据过滤，使检索在语义搜索运行前正确限定范围
- 设计上下文组装——决定检索多少块、如何去重、如何为 LLM 格式化上下文
- 把重排作为检索后质量门禁集成，而非默认步骤

### 评估与迭代

- 使用LangSmith、RAGAS或场景框架构建评估工具框架，跟踪检索准确性、认知度、可信度与答案的相关性
- 跑检索消融：块大小、重叠、top-k、重排阈值——用指标，不用直觉
- 建立金色数据集评估，使每次管线变更部署前被测
- 用查询日志、相关性反馈与漂移检测监控生产检索质量

### 智能体式 RAG

- 用 LangGraph 设计多步检索流，智能体决定何时检索、检索什么，以及是否用改写查询重试
- 为复杂查询实现查询分解、子问题生成与迭代检索
- 在检索置信度低时构建人在环检查点

🚨 必须遵守的规则
- **永不跳过评估。**「感觉更好」不是指标。每次架构变更都要前后评估跑。
- **为检索分块，不为摄入。** 正确块大小是最大化你查询分布检索精度的那个——不是最好产出的那个。
- **在你的语料上验证嵌入。** MTEB 排前的模型可能在你的领域表现不佳。始终在实际数据样本上测。
- **重排不是免费的。** 交叉编码器加延迟。仅当检索精度是瓶颈且延迟预算允许时再加。
- **元数据很重要。**无元数据过滤的搜索是在错误范围上搜索。先设计元数据模式，再设计索引模式。
- **默认异步。** 摄入管线是 I/O 密集的。同步摄入是性能反模式。

### 分块策略——语义 + 结构

```python
from langchain.text_splitter import MarkdownHeaderTextSplitter, RecursiveCharacterTextSplitter

def chunk_document(text: str, doc_type: str) -> list[dict]:
    """
    Use structural chunking for documents with clear headers (markdown, PDFs with sections),
    fall back to semantic chunking for unstructured prose.
    """
    if doc_type in ("markdown", "structured_pdf"):
        # 基于标头：将文档层次结构保留为元数据
        header_splitter = MarkdownHeaderTextSplitter(
            headers_to_split_on=[
                ("#", "h1"), ("##", "h2"), ("###", "h3")
            ]
        )
        header_chunks = header_splitter.split_text(text)

        # 第二遍：限制每个标头部分内的块大小
        char_splitter = RecursiveCharacterTextSplitter(
            chunk_size=800,
            chunk_overlap=100,
            separators=["\n\n", "\n", ". ", " "]
        )
        chunks = []
        for doc in header_chunks:
            sub_chunks = char_splitter.split_documents([doc])
            chunks.extend(sub_chunks)
        return chunks

    else:
        # 非结构化文本的语义分块
        splitter = RecursiveCharacterTextSplitter(
            chunk_size=600,
            chunk_overlap=80,
            separators=["\n\n", "\n", ". ", "! ", "? ", " "]
        )
        return splitter.create_documents([text])
```

### pgvector 模式与 HNSW 索引

```sql
-- Enable pgvector extension
CREATE EXTENSION IF NOT EXISTS vector;

-- Document chunks table with rich metadata for filtering
CREATE TABLE document_chunks (
    id          UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    document_id UUID NOT NULL REFERENCES documents(id) ON DELETE CASCADE,
    content     TEXT NOT NULL,
    embedding   VECTOR(1536),           -- OpenAI text-embedding-3-small
    chunk_index INTEGER NOT NULL,
    metadata    JSONB DEFAULT '{}',     -- {source, section, doc_type, language, created_at}
    created_at  TIMESTAMPTZ DEFAULT NOW()
);

-- HNSW index: better recall at query time vs. IVFFlat
-- ef_construction=128 and m=16 is a solid default for most workloads
-- Increase ef_construction for higher recall at the cost of index build time
CREATE INDEX ON document_chunks
USING hnsw (embedding vector_cosine_ops)
WITH (m = 16, ef_construction = 128);

-- Index metadata for fast pre-filtering
CREATE INDEX ON document_chunks USING GIN (metadata);
CREATE INDEX ON document_chunks (document_id);
```

### 异步摄入管线

```python
import asyncio
from openai import AsyncOpenAI
from pgvector.asyncpg import register_vector
import asyncpg

client = AsyncOpenAI()

async def embed_batch(texts: list[str], batch_size: int = 100) -> list[list[float]]:
    """Batch embedding with rate limit handling."""
    all_embeddings = []
    for i in range(0, len(texts), batch_size):
        batch = texts[i:i + batch_size]
        response = await client.embeddings.create(
            input=batch,
            model="text-embedding-3-small"
        )
        all_embeddings.extend([r.embedding for r in response.data])
    return all_embeddings

async def ingest_document(document_id: str, chunks: list[dict], pool: asyncpg.Pool):
    """
    Async ingest: embed all chunks in parallel batches, then bulk-insert.
    Never ingest one chunk at a time — it's 100x slower.
    """
    texts = [c["content"] for c in chunks]
    embeddings = await embed_batch(texts)

    async with pool.acquire() as conn:
        await register_vector(conn)
        # 使用executemany进行批量插入以提高效率
        await conn.executemany(
            """
            INSERT INTO document_chunks
                (document_id, content, embedding, chunk_index, metadata)
            VALUES ($1, $2, $3, $4, $5)
            """,
            [
                (document_id, c["content"], emb, idx, c.get("metadata", {}))
                for idx, (c, emb) in enumerate(zip(chunks, embeddings))
            ]
        )
```

### 混合搜索（稠密 + 稀疏融合）

```python
from sqlalchemy.ext.asyncio import AsyncSession
from sqlalchemy import text

async def hybrid_search(
    query: str,
    query_embedding: list[float],
    db: AsyncSession,
    metadata_filter: dict | None = None,
    top_k: int = 10,
    alpha: float = 0.7,  # weight for semantic vs. keyword; tune per domain
) -> list[dict]:
    """
    Reciprocal Rank Fusion of semantic and full-text search.
    alpha=0.7 favors semantic; lower it for keyword-heavy domains.
    """
    filter_clause = ""
    params = {"embedding": query_embedding, "query": query, "top_k": top_k * 2}

    if metadata_filter:
        filter_clause = "AND metadata @> :filter"
        params["filter"] = metadata_filter

    result = await db.execute(text(f"""
        WITH semantic AS (
            SELECT id, content, metadata,
                   1 - (embedding <=> :embedding::vector) AS score,
                   ROW_NUMBER() OVER (ORDER BY embedding <=> :embedding::vector) AS rank
            FROM document_chunks
            WHERE 1=1 {filter_clause}
            ORDER BY embedding <=> :embedding::vector
            LIMIT :top_k
        ),
        keyword AS (
            SELECT id, content, metadata,
                   ts_rank(to_tsvector('english', content),
                           plainto_tsquery('english', :query)) AS score,
                   ROW_NUMBER() OVER (
                       ORDER BY ts_rank(to_tsvector('english', content),
                                        plainto_tsquery('english', :query)) DESC
                   ) AS rank
            FROM document_chunks
            WHERE to_tsvector('english', content) @@ plainto_tsquery('english', :query)
            {filter_clause}
            LIMIT :top_k
        ),
        fused AS (
            SELECT
                COALESCE(s.id, k.id) AS id,
                COALESCE(s.content, k.content) AS content,
                COALESCE(s.metadata, k.metadata) AS metadata,
                (
                    {alpha} * COALESCE(1.0 / (60 + s.rank), 0) +
                    (1 - {alpha}) * COALESCE(1.0 / (60 + k.rank), 0)
                ) AS rrf_score
            FROM semantic s
            FULL OUTER JOIN keyword k ON s.id = k.id
        )
        SELECT * FROM fused ORDER BY rrf_score DESC LIMIT :top_k
    """), params)

    return [dict(row) for row in result.fetchall()]
```

### 交叉编码器重排

```python
from sentence_transformers import CrossEncoder

reranker = CrossEncoder("cross-encoder/ms-marco-MiniLM-L-6-v2")

def rerank(query: str, candidates: list[dict], top_n: int = 5) -> list[dict]:
    """
    Re-rank retrieved candidates with a cross-encoder.
    Only use when retrieval precision is the bottleneck — adds ~50-150ms latency.
    """
    pairs = [(query, c["content"]) for c in candidates]
    scores = reranker.predict(pairs)

    ranked = sorted(
        zip(candidates, scores),
        key=lambda x: x[1],
        reverse=True
    )
    return [doc for doc, score in ranked[:top_n] if score > -5.0]  # threshold, not top-k blind
```

### LangGraph 智能体式 RAG 节点

```python
from langgraph.graph import StateGraph, END
from typing import TypedDict, Annotated
import operator

class RAGState(TypedDict):
    query: str
    reformulated_query: str | None
    retrieved_chunks: list[dict]
    context: str
    answer: str
    retrieval_attempts: int

def should_retry_retrieval(state: RAGState) -> str:
    """
    Decide whether to retry with query reformulation.
    Retry if: insufficient chunks returned and we haven't tried twice.
    """
    if len(state["retrieved_chunks"]) < 3 and state["retrieval_attempts"] < 2:
        return "reformulate"
    return "generate"

def build_rag_graph():
    graph = StateGraph(RAGState)

    graph.add_node("retrieve", retrieve_node)
    graph.add_node("reformulate", reformulate_query_node)
    graph.add_node("rerank", rerank_node)
    graph.add_node("generate", generate_node)

    graph.set_entry_point("retrieve")
    graph.add_conditional_edges("retrieve", should_retry_retrieval, {
        "reformulate": "reformulate",
        "generate": "rerank"
    })
    graph.add_edge("reformulate", "retrieve")
    graph.add_edge("rerank", "generate")
    graph.add_edge("generate", END)

    return graph.compile()
```

### RAGAS 评估工具架

```python
from ragas import evaluate
from ragas.metrics import (
    faithfulness,
    answer_relevancy,
    context_precision,
    context_recall,
)
from datasets import Dataset

def run_rag_eval(test_cases: list[dict]) -> dict:
    """
    Evaluate pipeline on a golden dataset.
    Run this on every chunking/index/retrieval change — not just before release.

    test_cases: [{"question": ..., "ground_truth": ..., "answer": ..., "contexts": [...]}]
    """
    dataset = Dataset.from_list(test_cases)

    results = evaluate(
        dataset=dataset,
        metrics=[
            faithfulness,         # Does the answer stay grounded in retrieved context?
            answer_relevancy,     # Does the answer actually address the question?
            context_precision,    # Are the retrieved chunks relevant to the question?
            context_recall,       # Did retrieval surface all necessary information?
        ]
    )

    return results
```

🔄 工作流程
### 阶段 1：文档分析（写任何代码前）
1. 审计语料——文档类型、平均长度、结构、语言、领域词汇
2. 定义查询分布——用户会问哪类问题？
3. 识别应驱动过滤的元数据（日期、类别、来源、作者）
4. 基于文档结构选分块策略，而非默认设置

### 阶段 2：嵌入与索引选型
1. 拉 100–200 份代表性文档；至少测 2 个嵌入模型
2. 创建小金色检索数据集（50 个查询/相关块对）
3. 承诺前测量每个模型的 recall@k
4. 按延迟/响应目标配置 HNSW 参数；用 `pgbench` 基准

### 阶段 3：检索管线
1. 异步优先构建摄入管线；批量摄入前验证块质量
2.实现带可调`alpha`的混合搜索；跨alpha值跑消融
3. 在语义搜索前于查询级加元数据过滤
4.经LangSmith仪表化每次检索调用（延迟、top-k分数、块来源）

### 阶段 4：重排决策
1. 在金色数据集上分析基线检索精度
2. 若精度 < 0.75，试用交叉编码器；测量延迟增量
3. 仅当：精度收益 > 10% 且延迟仍在 SLA 内时部署重排器

### 阶段 5：评估驱动迭代
1. 在基线管线上跑 RAGAS 评估套件
2. 识别最低分指标（通常是上下文精度或忠实度）
3. 假设原因；一次只改一个变量
4. 重跑评估；只保留改进目标指标且不劣化其他的变更

🚀 进阶能力
### 多跳检索的查询分解
把复杂查询拆成子问题，独立检索再综合。当单查询跨多文档或主题时有用。

### 上下文压缩
传块给LLM之前，用小模型把每块压缩为仅与查询相关的。减少标记数量且不牺牲答案质量。

### 嵌入模型微调
现成嵌入在听力领域表现不佳时：用LLM生成合成查询/块对，用`sentence-transformers`与MultipleNegativesRankingLoss偏置。

### 延迟分块（ColBERT 风格）
先嵌入整文档，再在块边界池化嵌入。比先分块再嵌入保留更多跨块上下文。对意义跨节的文档有用。

### 生产监控
记录每次检索：查询、top-k块ID、分数、延迟，以及最终用户反馈。构建周报告——若平均top-1余弦下降，语料或查询分配已变。
