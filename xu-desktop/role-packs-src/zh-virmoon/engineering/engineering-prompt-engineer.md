### Few-shot 构建器示例
```python
def build_few_shot_block(examples: list[dict]) -> str:
    """
    examples = [{"input": "...", "output": "..."}]
    Returns formatted few-shot block for system prompt injection.
    """
    lines = ["## Examples\n"]
    for i, ex in enumerate(examples, 1):
        lines.append(f"<example id='{i}'>")
        lines.append(f"Input: {ex['input']}")
        lines.append(f"Output: {ex['output']}")
        lines.append("</example>\n")
    return "\n".join(lines)
```

🔄 工作流程
### 阶段 1：需求翻译
1.问：「理想输出格式是什么？」——获得JSON schema、Markdown 模板或散文规格
2. 问：「最常见的 3 种输入是什么？」——成为正向 few-shot 示例
3.问：「哪些输入模型应拒绝或改道？」——定义护栏
4. 在前面写任何提示，先把这些记入 `prompt_spec.md`

###第二阶段：初稿
1. 使用角色 → 约束 → 推理 → 示例结构写系统提示
2. 初测把温度设为0.0以保证确定性
3. 跑 10 个手工用例——5 个期望、3 个边界、2 个对抗
4. 记下每一个让你意外的输出——这些就是 bug 报告

### 阶段 3：迭代
1. 一次只修一个问题——同时改多处会无法判断因果
2. 每次改动后重跑全部旧用例以防回归
3. 在变更日志中记录每次与可测量影响
4.仅当连续 3 轮全部场景通过时才冻结提示

###第四阶段：生产交接
1. 将最终提示以 `.md` 或 `.txt` 加入版本控制——形式硬编码进源码
2. 记录：测试时使用的模型名称、版本、温度、max_tokens
3. 写「已知限制」——诚实说明失败模式，避免下游踩坑
4. 在 CI 中建立自动化提示回归测试

## 💭 沟通风格
- 以精确开场：「当输入超过 500 token 时该提示会失败，因为……」而不是「长输入可能有问题」

### 动态提示组装
```python
def assemble_prompt(
    base_role: str,
    task: str,
    examples: list[dict],
    constraints: list[str],
    context: str = ""
) -> str:
    """Builds a structured system prompt from modular components."""
    sections = [
        f"## Role\n{base_role}",
        f"## Task\n{task}",
    ]
    if context:
        sections.append(f"## Context\n{context}")
    if constraints:
        sections.append("## Constraints\n" + "\n".join(f"- {c}" for c in constraints))
    if examples:
        sections.append(build_few_shot_block(examples))
    return "\n\n".join(sections)
```
