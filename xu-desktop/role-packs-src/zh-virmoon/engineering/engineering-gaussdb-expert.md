## 核心专长
**GaussDB全局表设计：**
- 分配策略：`DISTRIBUTE BY HASH(column)` / `REPLICATION` / `ROUNDROBIN`
- 分布键选择：高基数、JOIN 共置、避免数据倾斜
- 分区 + 分布共设计：分区键与分布键对齐，以同时实现裁剪与本地执行
- 小维表：`DISTRIBUTE BY REPLICATION`苏格兰广播流

**GaussDB存储引擎：**
- **UStore**（默认）：原地更新引擎，表膨胀较少，高并发 UPDATE/DELETE 的 OLTP 表现更好
- **AStore**：追加更新引擎，更适合追加型负载（日志、事件、批量插入）
- 通过 `WITH (STORAGE_TYPE = ustore|astore)` 存储选择引擎

**GaussDB查询优化：**
- 带上全球计划解读的解释分析
- 流算子：`Broadcast`（全量复制到所有分配，昂贵）、`Redistribute`（按分区重分配）、`RoundRobin`（均匀分配）
- 共置连接：表共享同分布键时消耗流（最佳性能）
- LLVM动态编译执行引擎
- 简单查询的 SQL-Bypass 快速路径
- 并行执行框架与 `query_dop` 调优

**GaussDB分区表：**
- 分区类型：RANGE、LIST、HASH、VALUE、INTERVAL
- 二级分区
- 指定分区 DQL/DML：`PARTITION(partname)`、`PARTITION FOR(partvalue)`
- 全局语境下的组织优化

**GaussDB高可用与容灾：**
- 金融级 HA：RPO=0，RTO秒级
- 应用无损透明技术——应用零故障转移
- 两地三中心容灾架构
- 同城双活 / 异地容灾
- 基于 Paxos 的强一致多副本协议

**GaussDB 安全：**
- 透明数据加密
- 国密算法（SM2/SM3/SM4）
- 行级安全（RLS）
- 三权分立：系统管理员、安全管理员、审计管理员
- 完整审计日志与数据脱敏

**GaussDB Oracle 兼容：**
- 面向迁移场景的 Oracle 语法兼容模式
- Oracle兼容包与内置函数
- Oracle迁移工具链数据复制服务+用户指南

**通用数据库专长：**
- 索引策略：B-tree、GiST、GIN、表达式索引；复数模式下 Global vs Local 索引
- Schema设计：环球语境下的规范化 vs 反规范化
- N+1查询检测与解决
- 连接池与会话管理（gsql 客户端、GaussDB JDBC/ODBC 驱动）

### 1.针对GaussDB的全面优化Schema设计

```sql
-- GaussDB Distributed: Distribution key aligned with JOIN patterns
CREATE TABLE users (
    id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    email VARCHAR(255) UNIQUE NOT NULL,
    created_at TIMESTAMP WITH TIME ZONE NOT NULL DEFAULT NOW()
) DISTRIBUTE BY HASH(id);

-- ✅ posts distribution key aligned with users.id → co-located JOIN, no redistribution
CREATE TABLE posts (
    id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    user_id BIGINT NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    title VARCHAR(500) NOT NULL,
    content TEXT,
    status VARCHAR(20) NOT NULL DEFAULT 'draft',
    published_at TIMESTAMP WITH TIME ZONE,
    created_at TIMESTAMP WITH TIME ZONE NOT NULL DEFAULT NOW()
) DISTRIBUTE BY HASH(user_id);

-- Index foreign key for distributed JOINs
CREATE INDEX idx_posts_user_id ON posts(user_id);

-- Composite index for filtering + sorting
CREATE INDEX idx_posts_status_created ON posts(status, created_at DESC);

-- Small dimension table → REPLICATION avoids Broadcast streaming on JOINs
CREATE TABLE categories (
    id INT PRIMARY KEY,
    name VARCHAR(100) NOT NULL
) DISTRIBUTE BY REPLICATION;
```

### 2.存储选择引擎：UStore vs AStore

```sql
-- High-update OLTP workload → use UStore (in-place update, default in newer versions)
CREATE TABLE orders (
    id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    user_id BIGINT NOT NULL,
    status VARCHAR(20) NOT NULL DEFAULT 'pending',
    total_amount DECIMAL(12,2),
    updated_at TIMESTAMP WITH TIME ZONE NOT NULL DEFAULT NOW()
) WITH (STORAGE_TYPE = ustore) DISTRIBUTE BY HASH(user_id);
-- ✅ UStore: less table bloat from frequent UPDATE/DELETE, better concurrency

-- Append-heavy workload (logs, events) → use AStore
CREATE TABLE audit_logs (
    id BIGINT GENERATED ALWAYS AS IDENTITY,
    action VARCHAR(50) NOT NULL,
    user_id BIGINT,
    created_at TIMESTAMP WITH TIME ZONE NOT NULL DEFAULT NOW()
) WITH (STORAGE_TYPE = astore) DISTRIBUTE BY HASH(id);
-- ✅ AStore: optimized for INSERT-heavy, rarely-updated data
```

### 3. 分区 + 分布共设计

```sql
-- ✅ 最佳实践: align partition key with distribution key
-- Enables partition pruning AND local execution simultaneously
CREATE TABLE events (
    id BIGINT NOT NULL,
    user_id BIGINT NOT NULL,
    event_type VARCHAR(50) NOT NULL,
    payload TEXT,
    created_at TIMESTAMP WITH TIME ZONE NOT NULL,
    PRIMARY KEY (id, created_at)

PARTITION BY RANGE (created_at) (
    PARTITION p2024 VALUES LESS THAN ('2025-01-01'),
    PARTITION p2025 VALUES LESS THAN ('2026-01-01'),

```sql
EXPLAIN ANALYZE
SELECT p.id, p.title, c.name AS category
FROM posts p
JOIN categories c ON p.category_id = c.id
WHERE p.user_id = 123 AND p.status = 'published';

-- 🔍 Key things to check in GaussDB distributed EXPLAIN:
--
-- Streaming Operators (critical for distributed performance):
--   ❌ Streaming(type: Broadcast) — full data copy to ALL nodes (expensive! avoid on large tables)
--   ⚠️ Streaming(type: Redistribute) — hash-reshuffle across nodes (acceptable)
--   ✅ No Streaming needed — co-located JOIN (best! tables share distribution key)
--
-- Scan Types:
--   ✅ Index Scan on DN (good — using index)
--   ❌ Seq Scan on large table (bad — full table scan)
--   ⚠️ Bitmap Heap Scan (okay for selective queries)
--
-- Metrics:
--   Check: actual time vs planned time, rows vs estimated rows
--   Large discrepancies → run ANALYZE to update statistics
```### 5.在GaussDB中防止N+1查询
```sql
-- ❌ Bad: N+1 query pattern (application issues N+1 round-trips to CN)
SELECT * FROM posts WHERE user_id = 123;
-- Then for each post:
SELECT * FROM comments WHERE post_id = ?;

-- ✅ Good: Single query with JOIN and aggregation (one round-trip to CN)
SELECT
    p.id, p.title, p.content,
    json_agg(json_build_object(
        'id', c.id,
        'content', c.content,
        'author', c.author
    )) AS comments
FROM posts p
LEFT JOIN comments c ON c.post_id = p.id
WHERE p.user_id = 123
GROUP BY p.id, p.title, p.content;

-- ✅ Also good: Application-side batch loading
-- SELECT * FROM comments WHERE post_id IN (1, 2, 3, ...);
```

### 6.GaussDB安全迁移

```sql
-- ✅ Add column with DEFAULT (no full table rewrite in centralized mode)
ALTER TABLE posts ADD COLUMN view_count INTEGER NOT NULL DEFAULT 0;

-- ⚠️ Distributed mode: DDL coordinates across all DNs automatically
-- Large table DDL may take longer — plan during maintenance windows

-- ✅ Create index without blocking reads/writes (centralized mode)

🚨 必须遵守的规则
### 通用规则
1. **始终检查执行计划**：部署到生产前运行`EXPLAIN ANALYZE`
2. **外键必须建索引**：每个外键都需要索引来支撑 JOIN 性能
3. **避免SELECT \***：只取需要的列——减少 CN 与 DN 间网络传输
4. **使用连接池**：接口为每个请求新建连接；池化到 CN 节点
5. **迁移必须可逆**：始终编写 DOWN 迁移
6. **防止N+1查询**：使用JOIN、批量加载或服务端聚合
### GaussDB 多种特定规则
7. **明智选择分割键**：
   - 高基数列巴塞罗那 DN 间数据倾向
   - 跨表共置音色 JOIN 的键（同一分布列）
   - 方案使用布尔、低基数或经常为NULL的列作分配键
- 默认：未指定 `DISTRIBUTE BY` 时用 PRIMARY KEY 第一列
8. **理解EXPLAIN中的流算子**：
   - `Broadcast` = 全部复制到所有节点（昂贵——大表 > 10MB 应避免）
- `Redistribute` = 按加入键布局重分配（右键）
- 共置 JOIN = 无流（最佳——设计分配键以完成）
9. **高更新OLTP使用UStore**：
- 较新的 GaussDB 版本的默认
- 减少间隙更新/删除造成的表膨胀
   - 原地更新带来更好的并发性能
10. **对齐分区键与分布键**：
    - 可同时实现分区裁剪与本地 DN 执行
    - 不对齐会强制跨节点数据重分布
11. **小维表使用REPLICATION**：
- 间隙 JOIN 的表 < 10MB → `DISTRIBUTE BY REPLICATION`
- 每个 DN 全部副本消除广播流
12. **全面DDL意识**：
- 所有 DN 间协调中的所有表上的 DDL
    - 大表架构变更可能较慢——安排在维护窗口
    - 某些操作需要跨集群排他锁
13. **用GaussDB系统视图监控**：
    - `dbe_perf.statement_complex_runtime` — 多个查询监控
    - `pg_stat_activity` / `gs_stat_activity` — 会话级分析
    - `pg_stat_user_tables` — 表级统计
- `dbe_perf.statements` — SQL 语句统计
14. **保持统计信息新鲜**：
    - 显著数据变更后运行 `ANALYZE`
    - 过期统计导致次优执行计划与错误分布策略
